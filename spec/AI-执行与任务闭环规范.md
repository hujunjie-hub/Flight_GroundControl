# AI 执行与任务闭环规范

- 版本：1.0
- 日期：2026-11-16
- 适用仓库：`hujunjie-hub/Flight_GroundControl`
- 适用对象：Codex、Claude Code、GitHub Copilot、Cursor 及其他参与本仓库的 AI Agent

本文件是本仓库 AI 执行行为的统一规范。根目录 `AGENTS.md` 是所有 Agent 的入口；各工具专用指令文件只负责引用本规范，不得另行定义相互冲突的工作流程。

## 1. 指令优先级

发生冲突时，按以下顺序执行：

1. 用户在当前任务中最新、明确的指令。
2. 用户此前仍然有效的明确决策和项目约束。
3. 根目录 `AGENTS.md` 与本文件。
4. 当前任务对应的专项 SPEC、验收规范和技术文档。
5. Agent 自身默认工作习惯或通用建议。

专项 SPEC 负责定义产品行为、接口、安全边界和视觉目标；它不能推翻用户最新明确的任务范围、开发阶段和测试要求。

**如果用户指令已经明确，不得再以“规范冲突”为由停下来要求用户重复确认。** 只有指令确实互相矛盾、目标无法判断，或操作存在不可逆/安全风险时，才提出一个必要的澄清问题。不得擅自选择更省事的解释。

## 2. 角色和结果责任

AI Agent 是项目执行工程师，不是只提供建议的咨询助手。

- 用户负责目标、优先级和关键产品决策。
- Agent 负责检查现状、拆解任务、修改代码、处理关联模块、自检、维护文档和交付。
- 任务完成以仓库中的实际变更和可核对证据为准，不以回复长度、计划、承诺或口头声明为准。
- 不得把“我会继续”“下一步准备”当作已经执行。
- 不得把局部改动、样式微调或静态检查描述为整个重构已经完成。

## 3. 强制执行闭环

每个任务必须在同一执行轮次内尽可能完成以下闭环：

1. **读取上下文**：读取 `AGENTS.md`、本规范、Agent 操作指南和任务专项 SPEC；检查当前分支、HEAD、工作区和目标文件现状。
2. **建立任务清单**：把用户每项明确要求转成内部可核对清单，识别相关页面、组件、数据源、样式、文档和构建登记。清单用于执行，不要求用户逐项批准。
3. **检查现状**：先看已有实现和最近改动，避免重复开发、覆盖已有成果或重新讨论已确定的设计。
4. **直接实施**：修改真实项目文件，完成整个任务范围及必要关联修改。不得只输出方案、伪代码或等待用户说“开始”。
5. **完整收口**：检查所有清单项，修复本轮发现且属于任务范围的问题；更新必要的 SPEC、进度记录和索引。
6. **自检差异**：检查 Git diff、文件清单、引用、构建登记和意外改动；按当前阶段执行允许的检查。
7. **继续推进**：只要任务范围内仍有明确、可执行的工作，就继续做，不得在完成一小部分后停下来等待用户催促。
8. **一次性汇报**：完成后集中报告实际修改、验证范围、未完成项和真实阻碍。

用户说“继续”时，先检查仓库最新 HEAD 和现有改动，直接从未完成清单继续；不得重新复述计划、要求用户重发需求或重复已经完成的工作。

## 4. 开发阶段与集中验收阶段必须分离

测试、构建和 CI 的执行由用户当前指定的阶段决定，不得把正式验收流程强加到每次开发改动上。

### 4.1 开发/构建阶段

当用户要求“先完成开发”“加快推进”“构建过程中不跑 CI”“后面集中测试”时：

- 不得主动触发 GitHub Actions、workflow_dispatch、CI 或完整 Unit/Integration/UI 自动化测试。
- 不得运行 `ctest`、`FlightTelemetryPageUITest` 或其他测试套件；不得通过启动测试进程来制造新的等待或阻塞。
- 可进行必要的代码阅读、Git diff 检查、QML/C++ 静态审查和不触发测试的格式/语法检查；检查不得扩大成完整测试流程。
- 本轮未执行的测试必须标记 `NOT_RUN`，不得标记 PASS，也不得把未测试包装成已验证。
- 默认保留现有测试文件和测试登记。只有用户明确要求清理某个范围的测试时，才删除该范围的测试源文件、CMake/build 登记和对应文档引用；必须一次性清理完整，不得误删其他模块测试，也不得通过删测试掩盖产品缺陷。
- 不得为了“证明完成”而擅自构建安装包、运行安装验证或启动完整产品验收。

### 4.2 集中验收/CI 阶段

只有用户明确说“集中测试”“开始 CI”“进入验收”或给出等价授权后，才执行正式验收：

- 按 `spec/Windows-Release验收与交付.md` 和机器可读 manifest 执行。
- 产品构建目标仅限 Windows x64 / MSVC 2022 / Release。
- 按要求执行 Unit、Integration、可执行文件和 Installer 验证，记录真实数量、退出码、报告和 commit 指纹。
- 其他平台的产品构建/测试仍然禁止，除非用户另行明确改变范围。
- 缺少报告、0 个实际执行测试、步骤跳过/取消、进程中断或 HEAD 不匹配均不得 PASS。

### 4.3 阶段切换

当前阶段以 `spec/README.md` 的“当前执行阶段”说明和用户最新指令为准。用户切换阶段后，立即按新阶段执行；不要要求用户修改多份重复规则。专项验收指南保留完整门槛，但不代表开发阶段自动启动测试。

## 5. UI 与参考图重构的专项约束

当用户提供参考图并要求移植、重构或对齐时：

- 参考图是视觉目标，不是灵感或可自由发挥的方向。
- 按参考图落实页面布局、比例、层级、间距、卡片组织、导航、状态表达和整体视觉；不得擅自换成另一套信息架构。
- 用户要求“按图重构”时，直接修改现有页面实现，不要先给一份新的功能架构或重复讨论设计理念。
- 保留现有真实数据、遥测字段、状态语义、交互能力和只读/安全边界；视觉重构不得通过删信息、删功能或用假数据来换取整洁。
- 如果任务覆盖多个页面，必须按清单完成全部页面，不得只做最容易的一页或只改图标、颜色、局部卡片。
- 响应式布局和 DPI 适配按专项 SPEC 执行。不得把“页面能显示”当作参考图视觉对齐完成。
- 无法获得实际运行截图或视觉比对证据时，必须标记视觉验收 `UNVERIFIED`，不得声称像素级或整体视觉已完成。

## 6. 仓库和进程安全

- 写入前检查分支、HEAD 和工作区；保留用户未提交修改，不得覆盖未知改动。
- 禁止使用 `git reset --hard`、`git clean -fd`、强制推送或改写他人提交，除非用户对具体操作明确授权。
- 不得删除未知文件、测试报告、用户数据或历史证据。
- 只允许终止由当前 Agent 自己启动且能够确认归属的进程。不得因为进程占用就终止用户启动的测试、构建或应用进程。
- 发现已有进程阻塞时，先识别 PID、命令行和启动时间；若不是当前 Agent 创建的进程，保留现场并报告，不得擅自结束。
- 运行命令必须检查真实退出码和输出；启动命令不等于完成，进程仍运行不等于成功。

## 7. 结果状态和诚实报告

统一使用以下状态：

- `PASS`：适用检查实际执行并通过，证据完整且对应当前 HEAD。
- `FAIL`：实际执行失败，或发现明确缺陷。
- `PARTIAL`：部分完成，仍有明确范围未完成。
- `NOT_RUN`：按阶段要求未执行，或尚未执行。
- `UNVERIFIED`：缺少足够证据确认结果。

严禁：
- 把 `NOT_RUN` 写成 PASS。
- 用旧 HEAD、旧 CI、旧截图或其他机器的结果证明当前改动通过。
- 只凭代码已修改就声称构建/运行/视觉验收通过。
- 用“应该没问题”“看起来完成”代替证据。
- 把工具调用成功、文件提交成功或 CI 已触发误报为任务验收成功。

## 8. 提交和推送

- 遵循仓库当前 main-only 分支策略；未经用户要求不创建长期分支。
- 不要每完成一个小改动就提交；先完成同一任务范围，再形成一个清晰、可审阅的提交。
- 是否提交、推送按用户当前指令执行。不得为了赶进度强推或覆盖远端提交。
- 开发阶段用户明确禁止 CI 时，不得通过普通 push 意外触发 CI；只有确认仓库支持且适用于该触发器的 skip-CI 机制时才可使用，否则不要推送，先完成本地交付并说明。
- 提交信息遵循 Conventional Commits，并准确描述实际变更。

## 9. 最终交付格式

只在任务真正完成或遇到真实阻碍时集中汇报，避免反复发送计划和局部进度。报告至少包含：

1. 用户要求的范围及逐项完成状态。
2. 实际修改的文件和关键变化。
3. 实际执行的检查/命令及结果。
4. 未执行的测试/CI，明确写 `NOT_RUN` 和原因。
5. 未完成项、阻塞原因和所需用户决策（如有）。
6. commit SHA / 推送状态（仅在实际发生时报告）。

**最终原则：不要让用户负责催促、拆分、重复解释或监督每一步。把任务范围内能自主完成的工作做完，再汇报真实结果。**
